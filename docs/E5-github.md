# E5 · Multibranch, webhook e proteção de `main`

1. O projeto foi publicado no repositório público [DaviSouza78/carparts-jenkins-aula06](https://github.com/DaviSouza78/carparts-jenkins-aula06). Para integração contínua permanente, crie um GitHub App para o Jenkins com acesso somente a esse repositório e permissões mínimas de conteúdo/PR/status; armazene a credencial no cofre Jenkins. Evite token pessoal amplo.
2. Crie um item **Multibranch Pipeline** no Jenkins, fonte **GitHub**, proprietário/repositório, descoberta de branches e pull requests, `Jenkinsfile` na raiz. Confirme que o índice cria jobs para `main`, branch de recurso e PR.
3. Configure no GitHub um webhook `https://<domínio-da-equipe>/github-webhook/`, eventos *push* e *pull request*, tipo JSON e segredo HMAC. O exemplo `infra/nginx-webhook.conf` publica somente esse endpoint e encaminha ao Jenkins interno; a interface/API seguem acessíveis apenas por VPN/proxy autenticado. Configure a validação do segredo no plugin GitHub e confirme uma entrega de teste; não publique a porta 8080 diretamente.
4. A proteção clássica de `main` exige PR e mantém force push e exclusão desativados. Durante o ensaio, também exigiu o check `continuous-integration/jenkins/pr-merge` e branch atualizada. O GitHub bloqueou a PR desatualizada, depois a liberou quando o webhook iniciou o build verde. Para uso permanente, acrescente revisão independente, descarte aprovações antigas e mantenha um Jenkins acessível por webhook.

## Ensaio Multibranch local

Criei no Jenkins o item `carparts-multibranch-local`, com fonte Git local somente leitura `/project-git` e descoberta automática de branches. A configuração exportada está em `jenkins/multibranch-local.xml`; o `compose.yaml` monta apenas `.git` no controller e no agent, e `jenkins/gitconfig-lab` confia apenas nesse caminho. O índice encontrou `main` e `lab-branch-demo`, leu o Jenkinsfile de cada uma e iniciou dois builds, ambos `SUCCESS`. Consulte `evidence/live/multibranch-local-index.log`, `multibranch-local-summary.json` e os dois logs de build. `lab-branch-demo` é uma branch local criada para o ensaio e não representa o PR remoto.

**Evidência real:** o repositório ficou público em 30/09/2026 com autorização do proprietário. O GitHub Multibranch descobriu `main` e `PR-1`; `main #1` e `PR-1 #2`, `#3` e `#4` terminaram `SUCCESS`. O check `continuous-integration/jenkins/pr-merge` ficou verde na [PR #1](https://github.com/DaviSouza78/carparts-jenkins-aula06/pull/1). Um túnel Cloudflare temporário encaminhou apenas `/github-webhook/` ao proxy HMAC, que validou e entregou eventos `ping`, `pull_request` e `push`, todos com HTTP 200. O push da branch criou automaticamente o build `PR-1 #3`; ao atualizar a branch a partir de `main`, o check obrigatório ficou pendente, o webhook criou `PR-1 #4`, e o GitHub liberou o merge após o sucesso. Logs e resumo estão em `evidence/live/github-*`. A PR permanece aberta para revisão independente. **Após o ensaio**, a exigência do check foi retirada para não bloquear futuras PRs, o webhook foi desativado, o túnel e o proxy foram removidos, e a credencial Jenkins foi excluída. O proprietário escolheu deixar o token GitHub expirar em 01/10/2026. Para operação permanente, configure uma integração estável antes de reativar o check obrigatório. Fontes: [Jenkins Multibranch](https://www.jenkins.io/doc/book/pipeline/multibranch/), [GitHub webhooks](https://docs.github.com/en/webhooks/using-webhooks/creating-webhooks), [regras de proteção](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
